Centralized Multi-Screen Display Platform

A centralized display platform that brought live Tag-Scanning production KPIs, safety guidance and screen-specific media to shop-floor monitors and a large LED display. Users could simply drag files into the correct folder and specify on-screen duration in the filename; the software handled routing, playback and updates.

PythonFlaskSocket.IORaspberry PiLive Production KPIsFolder-Based MediaLinux
Centralized Display Manager Live production dashboards, safety messages and folder-driven media controlled across indoor and LED endpoints.

Engineering objective

Make live shop-floor KPIs visible where work happens, distribute safety information, and remove the need to individually update screens or configure playback settings.

My contribution

I developed centralized media routing, folder and filename-based playback control, Raspberry Pi display rendering, endpoint registration, heartbeat monitoring and remote refresh, alongside integration of live manufacturing dashboards.

Operational outcome

Operators and supervisors could view live Tag-Scanning production metrics on shared displays; staff could update safety notices and media by dropping files into screen-specific folders. The same platform served indoor screens and a large-format LED display.

Software architecture · two content sources

Tag-Scanning live KPI dashboards→ Display Platform→ Raspberry Pi / Browser Clients→ Indoor Screens + LED Display
Screen-Specific Media Folders→ Filename Playback Duration→ Automatic Media Discovery / Routing→ Assigned Displays

Live production dashboards originated from the separate Tag-Scanning System. The display platform delivered centrally managed views and media to endpoints; Socket.IO supported endpoint updates, status and remote commands.

Project overview

This software complemented the Tag-Scanning Manufacturing System by putting live production and KPI dashboards directly on screens around the plant. It also supplied safety guidelines and other visual notices through a self-service workflow: place an image, GIF or video in the designated display folder, include its desired display delay in the filename, and let the server discover, schedule and route it. The same centralized service supported indoor displays and a large LED matrix endpoint, with live monitoring and remote refresh.

Case 01

From manual screen updates to one central workflow

The user workflow was deliberately simple: put the right file into the corresponding display folder with its duration encoded in the filename. The software determined the destination, playback interval, media handling and screen update without requiring the user to edit code or visit a Raspberry Pi.

Screen-specific mediaEach display was associated with its own media folder and endpoint so content could be managed independently without hard-coding every screen into the user workflow.
Automatic discoveryThe server discovered configured media folders and generated the corresponding display routes automatically.
Drag-and-drop publishingUsers added, removed or renamed supported media inside a screen-specific folder. The server handled discovery and distribution without editing application code or visiting the display.
Filename-controlled timingMedia filenames encoded the requested delay, so the software could apply the desired on-screen duration automatically. Supported content included images, GIFs and MP4 video, with playback handling appropriate to the media type.

Case 02 · Manufacturing integration

Live Tag-Scanning KPIs and safety communication on shared screens

This platform was part of a wider digital manufacturing workflow. Tag-Scanning generated up-to-date production information; the display platform created shared production awareness for employees and supervisors while enabling self-service safety guidance and general media across multiple managed endpoints.

Production and department dashboardsLive manufacturing views from the separate Tag-Scanning System showed changing production status and KPIs without repeatedly preparing and circulating manual updates.
Safety guidanceStaff could publish safety notices and guidance using the same folder-based system, allowing information to appear on the intended screens without rebuilding the application.
Scalable display distributionFolder discovery and centralized rendering made it easier to expand or change display content without manually rewriting software or reconfiguring each screen. The same infrastructure served standard indoor screens and a large LED matrix display.
Accessible daily updatesNormal content changes required file placement rather than modifying HTML, restarting individual displays or reconfiguring Raspberry Pi clients.
The less obvious operational benefit was shared situational awareness: manufacturing KPIs were available where employees and supervisors worked, while safety communication used the same managed screen network. No percentage improvement in safety, productivity or decision speed is claimed without measured data.

Case 03 · Monitoring and control

Live status and remote display control

The browser-based Display Manager turned the system into an operational tool rather than just a slideshow server.

Heartbeat monitoringConnected displays periodically reported their screen identity, current media and last-seen state.
Online / stale / offlineThe manager translated heartbeat timing into a simple visual state so an operator could immediately see which endpoints needed attention.
Current mediaThe dashboard showed what each connected display was currently rendering.
Remote refreshIndividual displays or all displays could be refreshed from the central interface.

Case 04 · Reliability

Unattended display reliability

The endpoints were intended to run continuously, so the software included behavior for automatic media updates and recovery from common playback problems.

Folder monitoringChanges to media folders were detected and pushed to connected screens without rebuilding the application.
Real-time communicationSocket.IO handled update notifications, display registration, heartbeat reporting and refresh commands.
Playback resilienceVideo watchdog/fallback logic prevented a failed or stalled video from permanently stopping an unattended slideshow.
Endpoint modelRaspberry Pi/Linux clients ran the display view in kiosk-style browser sessions and received their assigned media from the central server. The same software stack served both indoor screens and the large-format LED display.
