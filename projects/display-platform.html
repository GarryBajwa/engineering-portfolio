Centralized Multi-Screen Display Platform

A custom server-side software solution developed to make multiple unattended displays simple for users to update, monitor and refresh from one central interface.

PythonFlaskSocket.IORaspberry PiLinux
Centralized Display Manager One interface for display status, current media, remote refresh and screen-specific control.

Engineering objective

Give users one practical place to manage content across multiple unattended screens without manually configuring each endpoint.

My contribution

I developed the centralized software workflow for media distribution, screen-specific rendering, display registration, heartbeat monitoring and remote refresh.

Operational outcome

The platform provided central visibility of connected-screen status and current media while serving both indoor screens and a large-format LED endpoint through Raspberry Pi clients.

Software architecture

User Media Folders→ Python / Flask Server↔ Socket.IO↔ Raspberry Pi / Browser Clients→ Assigned Displays
Project overview

Several unattended displays needed a simpler way to receive screen-specific media and report their operating status without manual updates at each endpoint. I developed a centralized Python/Flask platform for content delivery, heartbeat monitoring, current-media visibility and remote display control.

Case 01

From manual screen updates to one central workflow

The software was designed around the user’s real task: put the right media on the right screen, confirm that the screen is alive, and recover it remotely when needed.

Screen-specific mediaEach display was associated with its own media folder and endpoint so content could be managed independently without hard-coding every screen into the user workflow.
Automatic discoveryThe server discovered configured media folders and generated the corresponding display routes automatically.
Simple updatesUsers could add, remove or rename supported media files in the appropriate folder instead of editing application code or visiting each screen.
Mixed mediaThe rendering workflow supported images, GIFs and MP4 video, including configurable image timing and video playback handling.

Case 02

Live status and remote display control

The browser-based Display Manager turned the system into an operational tool rather than just a slideshow server.

Heartbeat monitoringConnected displays periodically reported their screen identity, current media and last-seen state.
Online / stale / offlineThe manager translated heartbeat timing into a simple visual state so an operator could immediately see which endpoints needed attention.
Current mediaThe dashboard showed what each connected display was currently rendering.
Remote refreshIndividual displays or all displays could be refreshed from the central interface.

Software Evidence

Case 03

Unattended display reliability

The endpoints were intended to run continuously, so the software included behavior for automatic media updates and recovery from common playback problems.

Folder monitoringChanges to media folders were detected and pushed to connected screens without rebuilding the application.
Real-time communicationSocket.IO handled update notifications, display registration, heartbeat reporting and refresh commands.
Playback resilienceVideo watchdog/fallback logic prevented a failed or stalled video from permanently stopping an unattended slideshow.
Endpoint modelRaspberry Pi/Linux clients ran the display view in kiosk-style browser sessions and received their assigned media from the central server. The same software stack served both indoor screens and the large-format LED display.
